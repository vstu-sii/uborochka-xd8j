# 2. Кандидаты моделей и бюджет

## 2.1. Критерии выбора

Ключевые критерии:
- **Стоимость запроса в токенах** — должна укладываться в бюджет Product'а (North Star метрика).
- **Качество распознавания деталей** — способность отличать тень от пятна, понимать контекст.
- **Задержка ответа** — приемлема для real-time проверки горничной (до 5 секунд).
- **Возможность локализации** — наличие российских альтернатив на случай санкций или требований к данным (152-ФЗ).
- **Деградация при лимите** — что происходит, когда токены кончаются.

---

## 2.2. Кандидат 1: GPT (OpenAI) — Облако (международное)

**Описание**: Самая дешевая мультимодальная модель OpenAI с поддержкой vision. Баланс цены и качества.

**Характеристики**:
- Поддержка изображений: да (low detail / high detail)
- Контекстное окно: 128K токенов
- Задержка: 1–3 секунды
- Языки: русский, английский

**Стоимость (актуально на 2026)**:
- Input: $0.15 / 1M токенов
- Output: $0.60 / 1M токенов
- Изображения: low detail = 85 токенов, high detail = 765–1105 токенов (зависит от размера)

**Расчет стоимости одного сценария**:
- Изображение (high detail, 1024×1024): ~1100 токенов
- Системный промпт + чек-лист: ~300 токенов
- Ответ (JSON): ~300 токенов
- **Итого input**: ~1400 токенов
- **Итого output**: ~300 токенов
- **Стоимость запроса**: 
  - Input: 1400 × $0.15/1M = $0.00021
  - Output: 300 × $0.60/1M = $0.00018
  - **Итого: $0.00039 ≈ 0.035 руб.** (при курсе 90 руб/$)
- **На 1000 проверок**: ~35 руб.

**Плюсы**:
- Высокое качество распознавания деталей
- Низкая стоимость
- Быстрый ответ
- Отличная документация и SDK

**Минусы**:
- Данные уходят в США (риск санкций, 152-ФЗ)
- Зависимость от внешнего API
- Возможные блокировки для российских юрлиц

## 2.3. Кандидат 2: GigaChat (Сбер) — Российское облако

**Описание**: Российская мультимодальная модель от Сбера с поддержкой изображений. Работает в российской инфраструктуре.

**Характеристики**:
- Поддержка изображений: да (в GigaChat Max)
- Контекстное окно: 32K токенов
- Задержка: 2–5 секунд
- Языки: русский (приоритет), английский

**Стоимость (актуально на 2026)**:
- Примерно 0.5–1.0 руб. за 1000 токенов (зависит от тарифа)
- Есть подписочные модели с фиксированной платой

**Расчет стоимости одного сценария**:
- Изображение: ~1100 токенов
- Системный промпт + чек-лист: ~300 токенов
- Ответ (JSON): ~300 токенов
- **Итого input**: ~1400 токенов
- **Итого output**: ~300 токенов
- **Стоимость запроса**: 
  - Input: 1400 × 0.7/1000 = 0.98 руб. (средняя цена)
  - Output: 300 × 0.7/1000 = 0.21 руб.
  - **Итого: ~1.2 руб.**
- **На 1000 проверок**: ~1200 руб.

**Плюсы**:
- Данные в РФ (соответствие 152-ФЗ)
- Нет риска санкций
- Русскоязычная оптимизация
- Техподдержка на русском

**Минусы**:
- Выше стоимость 
- Качество ниже, чем у GPT (особенно на сложных сценах)
- Меньше контекстное окно
- Возможны задержки при пиковых нагрузках

## 2.4. Кандидат 3: MiniCPM-V 2.6 (локально) — Реалистичный Open-source

**Описание**: Компактная мультимодальная модель (2.8B параметров), специально оптимизированная для запуска на потребительском железе. На бенчмарках показывает качество, близкое к моделям в 2–3 раза больше, но требует в разы меньше ресурсов.

**Характеристики**:
- Поддержка изображений: да (OCR, детекция объектов, описание сцен)
- Размер: 2.8B параметров 
- Требования: GPU с 8–12 GB VRAM (RTX 3060 / 4060 / Laptop GPU)
- Задержка: 1–4 секунды на consumer GPU
- Языки: русский (хорошая поддержка), английский, китайский

**Стоимость**:
- Лицензия: бесплатно (Apache 2.0)
- Инфраструктура: потребительский GPU + электричество

**Расчет стоимости (амортизация GPU)**:
- GPU RTX 4060: ~45,000 руб.
- При 1000 запросов/день: 0.041 руб./запрос
- Электричество: ~0.005 руб./запрос
- **Итого: ~0.05 руб./запрос**
- **На 1000 проверок**: ~50 руб. (CAPEX всего 45к на GPU)

**Плюсы**:
- **Низкий порог входа**: работает на ноутбуке или бюджетной видеокарте
- **Качество/цена**: лучшее соотношение для MVP и небольших объемов
- **Русский язык**: нативная поддержка, не требует перевода промптов
- **Полный контроль над данными**: ничего не покидает периметр
- **Быстрый старт**: запуск через Ollama / llama.cpp за 5 минут

**Минусы**:
- Качество ниже, чем у GPT-4o-mini на сложных сценах (тени, блики, мелкая пыль)
- Меньше контекста для длинных описаний
- Требует базовой настройки окружения (Docker / Ollama)
- Нет автоматического масштабирования (нужно добавлять GPU вручную)

## 2.5. Концепция локальной модели (MiniCPM-V 2.6)

Если выбираем локальную модель, что меняется в проекте:

### Данные:
- Все фото хранятся локально, не покидают периметр компании
- Можно собирать собственный датасет для дообучения (fine-tuning)
- Нет риска утечки через внешние API
- Полное соответствие 152-ФЗ без дополнительных согласований

### Железо:
- **Для старта**: RTX 3060 / 4060 (8–12 GB VRAM) — ~45,000 руб.
- **Для продакшена**: RTX 4090 или A10G — только при росте нагрузки >5000 проверок/день
- Масштабирование горизонтальное: добавляем дешевые consumer GPU, а не дорогие серверные
- Инфраструктура минимальна: Docker + Ollama, не нужен Kubernetes на старте

### Качество:
- Базовое качество достаточное для MVP: детекция мусора, белья, явных загрязнений
- На сложных сценах (тени, блики) качество ниже, чем у облачных VLM
- Стратегия улучшения: fine-tuning на 200–500 размеченных фото повышает точность на 15–20%
- Нужен процесс валидации: A/B тесты с GPT-4o-mini на первых 100 фото для калибровки

### Операционные расходы:
- CAPEX: 45,000 руб. на стартовую GPU (в 3–4 раза дешевле, чем для 7B моделей)
- OPEX: электричество (~500 руб./мес.), минимальная поддержка DevOps
- При 1000 проверок/день: ~50 руб./день (амортизация + электричество)
- При 5000 проверок/день: нужно 2 GPU, стоимость растет линейно, но остается низкой

### Когда выбирать локальную модель (MiniCPM-V):
- Есть требования 152-ФЗ или политики безопасности (данные не могут покидать периметр)
- Высокий риск санкций или нестабильности внешних API
- Бюджет на CAPEX ограничен (<100к руб.)
- Объем проверок до 5000/день 
- Нужен быстрый прототип без зависимости от вендоров
- Есть желание дообучать модель под свои специфические стандарты чистоты

## 2.6. Лимиты и деградация: что делаем, когда бюджет кончился

### Сценарий 1: Облачная модель (GPT / GigaChat)

**Что происходит при исчерпании лимита**:
- API возвращает ошибку 429 (Too Many Requests) или 402 (Payment Required)
- Запросы перестают обрабатываться
- Горничные не получают обратную связь
- Супервайзеры получают больше фото на ручную проверку

**План решения**:

#### 1. Мониторинг бюджета (проактивный подход)
- Реализовать счетчик токенов в реальном времени
- Настроить уведомления при достижении 70%, 80%, 90% бюджета
- Прогнозировать расход: если за утро потрачено 60% бюджета, к вечеру лимит кончится

#### 2. Приоритизация запросов (критичность vs стоимость)
Не все проверки одинаково важны. При ограничении бюджета система должна решать, какие фото проверять в первую очередь:
- **Высокий приоритет**: Номера для VIP-гостей, номера с предыдущими жалобами, первые проверки дня (базовая линия)
- **Средний приоритет**: Стандартные номера, повторные проверки после исправлений
- **Низкий приоритет**: Номера, которые уже проверены супервайзером вручную, технические помещения

При приближении к лимиту система обрабатывает только высокий и средний приоритет, низкий отправляется на ручную проверку.

#### 3.  Ручная проверка 
- При исчерпании лимита система автоматически помечает фото как "требует ручной проверки"

#### 4. Кэширование результатов (экономия на повторах)
- Если одно и то же фото уже проверялось (например, горничная переотправила его), возвращать кэшированный результат
- Кэш по хэшу изображения: одинаковые фото = одинаковый результат

---

### Сценарий 2: Локальная модель (MiniCPM-V 2.6)

**Что происходит при исчерпании лимита**:
- Лимита токенов нет (модель локальная, нет оплаты за запрос)
- Но есть лимит производительности GPU (задержки растут при высокой нагрузке)
- При перегрузке GPU модель работает медленно (10–30 секунд вместо 2–5)
- В крайнем случае — падение сервиса 

**План решения**:

#### 1. Мониторинг производительности GPU
- Отслеживать в реальном времени: загрузку GPU, использование памяти, температуру
- Уведомления при достижении 80% загрузки GPU
- Прогнозирование: если загрузка стабильно >70%, нужно масштабирование

#### 2. Очередь запросов (сглаживание пиков)
- При высокой нагрузке запросы не отклоняются, а встают в очередь
- Горничная получает уведомление: "Проверка выполняется, ожидайте 10–15 секунд"
- Приоритизация в очереди: VIP-номера обрабатываются первыми
- Максимальное время ожидания в очереди: 30 секунд 


#### 3. Батчинг запросов (оптимизация загрузки GPU)
- Вместо обработки каждого фото по одному — группировка запросов
- Батч из 4–8 фото обрабатывается одновременно (если позволяет память GPU)
- Снижение задержки на 30–40% при высокой нагрузке

#### 4. Кэширование результатов 
- Одинаковые фото → кэшированный результат
- Экономия вычислительных ресурсов GPU
- Срок жизни кэша: 24 часа
