# ADR-001: Изоляция внешних систем через ACL-адаптеры, доступ к БД только через Repo

## Статус
Принято — 2026-09-28.

## Контекст

При проектировании C4-диаграммы контейнеров (`docs/architecture/container.puml`)
для «Уборочки» встал вопрос: как оформить связи с двумя внешними системами
(Telegram Bot API и AI Vision Model) и с базой данных так, чтобы архитектура
была одновременно:

- реалистичной для Telegram-бота с AI-анализом фото;
- проверяемой машиной (`aact check` из `aact.config.ts`), а не только
  «на глаз»;
- устойчивой к смене поставщика (Telegram → другой мессенджер,
  одна AI-модель → другая) без переписывания домена.

Решение фиксируется здесь, потому что оно накладывает жёсткое ограничение
на дальнейшую разработку: где заканчивается домен и начинается интеграция.

## Рассмотренные варианты

**A. `Bot Orchestrator` сам стучится в Telegram и в БД.**
Проще на старте — на один слой меньше. Отклонён: любое изменение API
Telegram или схемы хранения задевало бы код, который отвечает за бизнес-
логику оценки. `aact` (правило `acl`) прямо флагует такие связи как
нарушение — не только по вкусу, а по факту завязки домена на чужой контракт.

**B. Domain-сервис изолирован через ACL-адаптеры и Repo (выбрано).**
`Telegram Adapter` — единственная точка, которая знает формат вебхука и
Bot API; `Vision Client` — единственная точка, которая знает формат запроса
к AI-модели; `Assessments Repo` — единственная точка, которая пишет SQL.
`Bot Orchestrator` работает только с их доменными интерфейсами.

**C. Асинхронная шина событий между всеми контейнерами.**
Избыточно для нагрузки одного Telegram-бота: усложняет отладку и деплой
(нужен брокер) без соразмерной выгоды. Отклонён на этом масштабе, но
зафиксирован как следующий шаг, если появится второй канал доставки
(e-mail, веб-виджет) — тогда события оправданы.

## Решение

1. Все вызовы наружу (Telegram, AI-модель) идут только через контейнеры,
   помеченные как ACL (`Telegram Adapter`, `Vision Client`) — это
   проверяется правилом `acl` в `aact.config.ts`.
2. Каждый такой вызов явно маршрутизируется «через API Gateway»
   (см. технологию связи в `container.puml`) — проверяется правилом
   `apiGateway`. Это не требует физического Gateway-сервиса на этом этапе:
   достаточно единой точки исходящих HTTP-вызовов с общими retry/timeout
   политиками внутри самого адаптера; когда/если появится второй внешний
   канал, это станет отдельным сервисом без изменения диаграммы контейнеров.
3. Единственный доступ к `Assessments DB` — через `Assessments Repo`
   (правила `crud` и `dbPerService`). `Bot Orchestrator` не хранит и не
   параметризует SQL.
4. Граф связей между контейнерами — ациклический (правило `acyclic`):
   запрос и ответ в рамках одной интеграции показаны одной связью, а не
   парой встречных — это и требование инструмента, и более честное
   отражение того, что запрос/ответ — одна логическая операция.

## Цена решения

- Два лишних контейнера (`Telegram Adapter`, `Vision Client`) по
  сравнению с вариантом A — больше файлов, один лишний прыжок вызова на
  каждую внешнюю интеграцию.
- Замена Telegram на другой мессенджер или одной AI-модели на другую
  требует переписать только соответствующий адаптер/клиент — домен и
  репозиторий не трогаются. Это и есть цель платы из предыдущего пункта.
- `Bot Orchestrator` не может напрямую оптимизировать SQL-запрос под
  свою бизнес-логику (например, батчинг) — любая такая оптимизация
  проходит через контракт `Assessments Repo`, что иногда означает
  расширение этого контракта, а не точечный хак в domain-слое.

## Как это проверяется

```bash
cd /  # корень репозитория
npx aact check    # 0 violations — источник: docs/architecture/container.puml
```

Конфигурация — `aact.config.ts` в корне репозитория. Правила включены:
`acl`, `acyclic`, `apiGateway`, `crud`, `dbPerService`, `cohesion`,
`commonReuse`.
